# design-sync notes

## Fixes

- [GENERAL] Build produced 0 matched components (`[TITLE_UNMAPPED]` dropped Button/Badge/IconButton, `exported PascalCase symbols: 0`) → root cause: `package.json` only declared types via the `exports["."].types` map, with no top-level `types`/`typings` field. The converter's `.d.ts` entry resolution (`lib/dts.mjs`'s `findTypesRoot`/`projectFor`) checks `publishConfig.types`, then `pkgJson.types`/`typings`, before falling back to scanning `dist/` — with neither set it defaulted to a nonexistent `<pkgDir>/index.d.ts` and found zero exports → fix: added a top-level `"types": "./dist/index.d.ts"` field to `package.json` (harmless, standard dual-compat practice for packages that also use the `exports` map). Re-run after this fix: 3/3 components matched cleanly.

- **This has now regressed once (0.3.5).** The `types` field was dropped again while adding the `./standalone.css` subpath export, and the sync silently produced a 0-component "tokens-only DS" that would have DELETED all 3 components from the Claude Design project. **Whenever `package.json`'s `exports` map is edited, confirm the top-level `"types": "./dist/index.d.ts"` survived** — it sits directly above `files`/`exports` and is easy to lose in a rewrite. Symptom to watch for in the build log: `exported PascalCase symbols: 0` followed by `[TITLE_UNMAPPED]` and `components: 0`.

- [GENERAL] **The shipped CSS is `dist/standalone.css`, not the Storybook scrape** (changed 0.3.5 sync). Previously `[CSS_FROM_STORYBOOK]` scraped the storybook build, which is Tailwind-JIT'd — it only contained classes the stories happened to use, so the design agent could write `text-body-lg` / `text-fg-error` / `bg-container-success` and get silently unstyled output. `src/standalone.css` force-emits the whole token vocabulary via `@source inline(...)` and also picks up component utilities by scanning `src/`, so `cfg.cssEntry` points at its build output. **When a semantic token is added or renamed, add it to the `@source inline` list in `src/standalone.css`** or it won't be emitted and the design agent can't use it.
- [GENERAL] **`src/standalone.css` includes Tailwind preflight — keep it that way.** It originally omitted preflight ("additive, meant to layer onto a host environment"), which made Ghost Button render with the browser's default black `<button>` border and As Link render with the default `<a>` underline. Both were caught only by the storybook comparison — the render check passes either way, so **a missing reset is invisible to every gate except the compare loop.** The fix is one line in `src/standalone.css` (`@import "tailwindcss/preflight.css" layer(base);`), on the reasoning that a consumer with no Tailwind build has no reset either, so this is the same problem rather than a special case. A brief detour shipped it as a separate `standalone-reset.css` file/export/script; that was reverted in favour of the single stylesheet — don't reintroduce the split.
- Switching `cssEntry` off the storybook scrape also drops the inlined `@font-face` rules that scrape carried, firing `[FONT_MISSING]` for "Inter Variable". Fixed with `cfg.extraFonts: ["./node_modules/@fontsource-variable/inter/index.css"]`. This warning is invisible to the compare oracle (both panels fall back to the same system font), so never dismiss it as cosmetic.

## Re-sync risks

- Story count is tiny (3 components, Button/IconButton/Badge under `src/components/atoms/`) — as the library grows, new `atoms/molecules/sections` dirs will need no config changes (component discovery is automatic from storybook `index.json`). The `types`-field regression above is the standing risk, not component growth.
- **`cfg.buildCmd` is `npm run build:dist`** — it must stay a command that builds both artifacts the sync consumes (`dist/index.js` + `.d.ts` via `build:lib`, and `dist/standalone.css` via `build:styles`). A sync run against a stale `dist/standalone.css` ships yesterday's token vocabulary with no warning, since the converter just copies whatever file is there. If a new build script is added, keep `build:dist` as the aggregate.
- `conventions.md` enumerates the token class vocabulary for the design agent, and every name in it was grep-verified against `ds-bundle/_ds_bundle.css` on this sync. That check only passes because `standalone.css` force-emits them — so **re-run the verification whenever the `@source inline` list changes**, or the header will promise classes that no longer ship.
- All 9 Button stories and all 7 IconButton stories were graded from fresh screenshot pairs (raised `--max-stories` above the default cap of 6) — no story caps left un-graded for either component.
- Storybook still renders from `src/index.css` (JIT), while the sync ships `standalone.css` (full vocabulary + preflight). The two are intentionally different stylesheets, so `[REFERENCE_STALE?]` can appear on a sync where only the CSS entry moved — that specific case is benign. It is NOT benign when DS source changed; rebuild `.design-sync/sb-reference` then.
- No `docsDir`/docs matched (0/3) — this repo has no per-component markdown docs directory; `.prompt.md` files are generated straight from `.d.ts` + stories, which is expected for this repo's shape.
- **Storybook `parameters.docs.description` does NOT reach the design agent — use a sibling `<Name>.md` instead.** Discovered on Badge (0.3.6, commit 749d2c0): the converter never reads `parameters.docs.*`, so component- and story-level descriptions set that way don't reach `.prompt.md`/`.d.ts` (the story-level ones leak in only incidentally, as text inside the pasted story source). **Confirmed fixed** (commit 2edb301): adding `src/components/atoms/badge/Badge.md` — sibling to `Badge.stories.tsx`, no config — was auto-discovered by `docsDir`/sibling lookup (`docs: 1/3 components matched` in the build log) and its body now replaces the synthesized `## Examples` dump in `Badge.prompt.md` verbatim, with `## Props` still appended since the doc has no props section of its own. Badge.md is marked auto-generated from Figma (`file TAEpKurZNTd8QzhDvheWlH, node 188:24042` — do not hand-edit, regenerate from Figma instead). **Applied to all 3 components** (commit d43a93b): `Button.md` and `IconButton.md` added beside their `.stories.tsx` files — `docs: 3/3 components matched` in the build log, all three `.prompt.md` now carry real prose. Confirmed again: no re-grade triggered (renderHash/sourceKey unchanged for all 3; only the sourceHash-based upload diff caught the two new files).

- **Per-token description comments do NOT survive into the shipped CSS — do not repeat this for other DSes without checking their own CSS pipeline.** The same commit (d43a93b) added `/* ... */` usage comments above every `--semantic-*` declaration in `semantic.css` (colours + typography), sourced from Figma the same way as the `.md` files. **Verified stripped**: `_ds_bundle.css` in the built output contains zero of these comments. Root cause is NOT `--minify` (confirmed by testing an unminified `tailwindcss` build — comments were still gone) and NOT specific to `@theme` blocks (confirmed by testing a comment on a completely plain `:root { --var: ...; }` declaration with no Tailwind directive involved — still stripped). **The Tailwind v4 CLI strips all plain CSS comments unconditionally**, as part of its own build pipeline, before the sync converter ever reads the file — there is no config knob in `.design-sync/config.json` that can recover this; `cssEntry` just points at whatever file the DS's own build produces, and by the time that file exists the comments are already gone. If per-token descriptions are wanted in the future, they need a different delivery mechanism entirely — e.g. a structured sidecar (JSON/YAML mapping token name → description) that a new discovery+emit step reads directly, bypassing the CSS build pipeline altogether. Source comments in `semantic.css` are still worth keeping for engineers reading the file locally; just know they are decorative only as far as this sync (and anything downstream of `npm run build:styles`) is concerned.
- Toolchain assumed: Node v24.9.0, Storybook 10.4.6, Tailwind v4 (`@theme` at-rules — lightningcss can't minify them during `vite build`, which is a harmless warning, not an error).
